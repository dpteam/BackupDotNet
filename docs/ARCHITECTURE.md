# Архитектура

## Общая картина

                    │  └─────┬──────┘  └─────────┬──────────┘  │
                    │        │                   │             │
                    │  ┌─────▼──────┐  ┌─────────▼──────────┐  │

## Проекты

| Проект | Ответственность | Зависит от |
|---|---|---|
| `BackupDotNet.App` | exe, режимы запуска, службы Windows, CLI | Core, Web, Deploy, Manage |
| `BackupDotNet.Core` | коллекторы, планировщик, политики, хранилище, JSON, журнал, брендинг | — |
| `BackupDotNet.Web` | HTTP-сервер, REST API, авторизация, роли, аудит | Core, Deploy, Manage |
| `BackupDotNet.Deploy` | установка агентов по WinRM, сканирование, AD | Core |
| `BackupDotNet.Manage` | очередь операций управления с подтверждением | Core, Deploy |

Зависимости строго в одну сторону: `App → Web → {Deploy, Manage} → Core`.
`Core` не знает ни о вебе, ни о развёртывании.

## Поток данных

1. **Планировщик** (`Scheduler`) раз в `tickSeconds` выбирает источники, у которых
   истёк интервал, и запускает их параллельно (`maxParallelChecks`).
2. **Коллектор** (`ICollector`) получает `Company` + `Source` + `AgentCtx`
   и возвращает `List<CollectResult>` — по одному на «задание» (job).
3. **PolicyEngine** сравнивает результат с предыдущим состоянием (`JobState`):
   свежесть, размер, серия неудач — и выносит вердикт `OK/WARN/FAIL/NODATA/SKIP`.
4. **DataStore** пишет `BackupRun` в историю и обновляет `JobState`.
5. **Zabbix** (если включён) отправляет значения; при недоступности — в очередь на диске.
6. **Веб-интерфейс** читает агрегаты (`/api/summary`, `/api/month`, `/api/uptime`, `/api/journal`).

## Ключевые типы

### `ICollector`

```csharp
public interface ICollector
{
    string Type { get; }
    List<CollectResult> Collect(Company company, Source source, AgentCtx ctx);
}
```

Регистрация — в `Collectors` (статический конструктор). Порядок регистрации
не важен, тип — ключ словаря без учёта регистра.

### `CollectResult`

Результат одной проверки: `Job`, `Kind`, `Reachable`, `SizeBytes`, `Message`,
`Errors`, `Details` (произвольные поля для интерфейса), `ResponseMs`.

Коллектор **не решает**, упало ли задание — он только сообщает факты.
Вердикт выносит `PolicyEngine`, зная политику компании.

### `JobState`

Текущее состояние задания: статус, время последнего успеха, размер,
серия неудач, длительность. Живёт в `<dataDir>\state\`.

### `BackupRun`

Один прогон: время, статус, размер, длительность, сообщение.
Живёт в `<dataDir>\history\` (по дням) и в агрегатах.

## Хранилище

```
<dataDir>/
├─ state/          # текущее состояние заданий (NDJSON)
├─ history/        # прогоны по дням
├─ month/          # суточные агрегаты для таблицы
├─ audit/          # журнал действий пользователей
├─ cache/          # временные файлы ZIP-проверок
└─ logs/           # журналы агента
```

Формат — NDJSON (по объекту в строке): дописывание дешёвое, повреждение одной
строки не убивает файл. Запись — атомарная (`File.Replace` через `.tmp`).

## Журналирование

`Log` — обёртка над `TraceSource`:

- `EnsureSource()` создаёт `TraceSource` и **очищает** листенеры по умолчанию
  (иначе `DefaultTraceListener` открывает окна Assert).
- `Init()` идемпотентен: листенеры создаются один раз, повторный вызов только
  обновляет настройки. Это закрывает классический баг «каждая строка пишется N раз».
- Два листенера: `ConsoleLogListener` (цвет по уровню, ошибки в stderr)
  и `FileTraceListener` (один открытый поток, ротация по размеру).
- Оба наследуются от `PlainTraceListener`, который переопределяет `TraceEvent`
  и печатает **только сообщение** — без префикса «Источник EventType: id :».
- `FileShare.ReadWrite | Delete` — журнал можно читать во время работы агента.

## Валидация конфигурации

Две проверки, которые дополняют друг друга:

| Где | Что делает |
|---|---|
| `CompanyValidator` (ядро) | статический разбор: поля компании, политика, параметры источников |
| `Normalize` (веб) | приведение к канону и проверка при сохранении |

`POST /api/company/validate` (с `?id=<id>` при редактировании) возвращает:

```json
{
  "ok": false,
  "errors": ["человекочитаемый список для сохранения"],
  "fields":   [{ "field": "src.0.host", "message": "укажите хост", "sourceId": "tcp" }],
  "warnings": [{ "field": "policy.freshnessHours", "message": "свежесть меньше 2 часов…" }]
}
```

`field` — путь в терминах формы: `name`, `id`, `policy.freshnessHours`,
`src.<индекс>.<параметр>` (включая вложенные: `src.0.ftp.host`).
По этому пути интерфейс находит input и подсвечивает его.

Что проверяется помимо обязательных полей:

| Проверка | Уровень |
|---|---|
| ID занят другой компанией (кроме самой редактируемой) | ошибка |
| Удалённый агент из `remoteAgent` не зарегистрирован | ошибка |
| Неизвестный тип источника | ошибка |
| Повтор ID источника или имени задания | ошибка |
| Пути/маски, относительный путь вместо абсолютного | ошибка / предупреждение |
| URL без `http(s)://`, порт вне 1–65535 | ошибка |
| Нет секрета для источника, которому он нужен | предупреждение |
| Пароль открытым текстом вместо `secrets.json` | предупреждение |
| Несколько источников одного типа без ID | предупреждение |
| Маски в списке служб (`inventory`) | ошибка |

Форма вызывает проверку с задержкой 400 мс на ввод, снимает старые метки,
красит поля и показывает панель итога. Отправка блокируется, если есть ошибки;
предупреждения не мешают сохранять.

## Перенос конфигурации

Инсталляция редко живёт на одной машине: центральный агент, филиалы, тестовый стенд.
Чтобы не переписывать десять файлов руками, конфигурация переносится одним ZIP.

### Из интерфейса

**Настройки → Конфигурация**:

1. «Скачать архив» — получить ZIP. Галочка «с секретами» добавляет `secrets.json`
   (спросит подтверждение — в архиве будут пароли источников).
2. «Импорт…» — выбрать ZIP. Сначала показывается **предпросмотр**: для каждого файла
   действие — `новый`, `будет заменён` или `без изменений`, плюс манифест архива
   (продукт, версия, дата создания).
3. «Применить» — запись. Текущая конфигурация предварительно сохраняется в
   `<dataDir>\backups\config-before-import-<дата>.zip`.

Изменения применяются без перезапуска службы: конфигурация перечитывается сразу.

### API

| Метод | Что делает |
|---|---|
| `GET /api/config/export` | ZIP с конфигурацией |
| `GET /api/config/export?secrets=1` | то же, с секретами |
| `GET /api/config/export?companies=acme,beta` | только выбранные компании |
| `POST /api/config/import?dryRun=1` | проверить, ничего не меняя |
| `POST /api/config/import` | применить |
| `POST /api/config/import?secrets=1` | применить, включая секреты |

Тело запроса — сам ZIP (`Content-Type: application/zip`). Требуется роль `admin`.

```powershell
# перенос на другую машину
Invoke-WebRequest http://old:8080/api/config/export -WebSession $s -OutFile cfg.zip
Invoke-WebRequest http://new:8080/api/config/import -Method POST -WebSession $s2 `
  -ContentType application/zip -InFile cfg.zip
```

### Что внутри архива

```
manifest.json          # формат, продукт, версия, дата, машина
settings.json
branding.json
env.json
secrets.json           # только при secrets=1
companies/<id>.json    # все компании, кроме файлов на «_»
```

### Правила, которые соблюдаются сознательно

- **Секреты — только по явному запросу.** По умолчанию их в архиве нет.
- **Импорт не удаляет.** Компании из архива добавляются или перезаписываются;
  компании, которых в архиве нет, остаются на месте. Удаление — отдельное действие.
- **Перед записью — резервная копия.** Неудачный импорт всегда можно откатить,
  путь к копии возвращается в ответе и показывается в интерфейсе.
- **Проверка JSON до записи.** Битый файл в архиве отклоняет весь импорт:
  частично применённой конфигурации не бывает.
- **Защита от «zip slip».** Имена записей проверяются; `..` в пути — отказ.
- **Атомарная запись.** Через `ConfigLoader.AtomicWrite`: недописанных файлов не остаётся.

## Уведомления

Два канала, обе настройки — в `config/settings.json` → `notifications`:

| Канал | Реализация |
|---|---|
| SMTP | `System.Net.Mail` (входит в .NET), без внешних библиотек |
| Telegram | обычный HTTPS-запрос к Bot API через `HttpWebRequest` |

```json
{
  "notifications": {
    "enabled": true,
    "on": { "fail": true, "warn": true, "recover": true, "nodata": false },
    "minIntervalMinutes": 30,
    "quietHours": { "from": "23:00", "to": "07:00" },
    "smtp": {
      "enabled": true,
      "host": "mail.example.org",
      "port": 587,
      "useSsl": true,
      "username": "backup@example.org",
      "passwordSecret": "smtp-password",
      "from": "backup@example.org",
      "to": ["admin@example.org", "noc@example.org"]
    },
    "telegram": {
      "enabled": true,
      "tokenSecret": "telegram-token",
      "chats": ["-1001234567890"]
    }
  }
}
```

Пароль SMTP и токен бота лучше держать в `config/secrets.json` (ключи
`passwordSecret` и `tokenSecret`), а не открытым текстом.

### Правила отправки

Это самая важная часть — без них уведомления превращаются в шум и их отключают.

1. **Только смена состояния.** Уведомление уходит при переходе в `FAIL`, `WARN`,
   `NODATA` или при восстановлении в `OK`. Если задание остаётся в `FAIL`,
   второго письма не будет.
2. **Первое появление задания тоже событие.** Если задание впервые видно и сразу
   падает — уведомляем (раньше молчали, это была ошибка).
3. **Подавление повторов.** Одно и то же событие по одному заданию — не чаще
   `minIntervalMinutes`. Отметки хранятся в `state/notify-throttle.json`,
   поэтому перезапуск агента не вызывает повторную рассылку.
4. **Тихие часы.** В указанном окне не будим. Восстановление — исключение:
   хорошие новости можно и ночью. Поддерживается переход через полночь (`22:00–07:00`).
5. **Очередь на досылку.** Если SMTP или Telegram недоступны, событие пишется в
   `state/notify-queue.ndjson` и досылается на следующем тике (до 50 за раз).

### Пробная отправка

**Настройки → Уведомления → Отправить тест** (или `POST /api/notify/test`).
Проверять канал нужно до первой настоящей аварии, а не во время неё.

### Как проверить без реального SMTP

В комплекте есть приёмник для локальных тестов:

```powershell
powershell -ExecutionPolicy Bypass -File tools\smtp-test-server.ps1
```

Слушает `127.0.0.1:2525`, письма складывает в `%TEMP%\smtp-capture.txt`.
В настройках укажите `host: 127.0.0.1`, `port: 2525`, `useSsl: false`.

## Бэкапы Hyper-V

Первый шаг от наблюдения к действию: агент умеет **делать** бэкап, а не только
проверять чужой.

### Как это работает

Экспорт через WMI `Msvm_VirtualSystemManagementService.ExportSystemDefinition` —
штатный механизм Hyper-V. Он сам собирает конфигурацию, диски и состояние ВМ
в один каталог, и не требует останавливать машину.

```
POST /api/backup/run { "engine": "hyperv-export", "target": "BND_TEST_01",
                       "destination": "H:\\Backups" }

H:\Backups\BND_TEST_01_2026-11-16_00-07-19\
├─ Virtual Hard Disks\BND_TEST_01.vhdx
└─ Virtual Machines\<GUID>.vmcx / .vmgs / .VMRS
```

Каждое задание получает свой каталог с датой — копии не перемешиваются,
а старые можно удалять по политике хранения целиком.

### API

| Метод | Что делает |
|---|---|
| `GET /api/backup/engines` | список движков и их доступность с причиной |
| `GET /api/backup/targets?engine=hyperv-export` | что можно скопировать (ВМ и их состояние) |
| `GET /api/backup/jobs` | очередь и история заданий |
| `POST /api/backup/run` | поставить задание в очередь |
| `POST /api/backup/cancel` | попросить задание остановиться |
| `GET /api/backup/retention` | политика хранения и текущие копии |
| `POST /api/backup/retention/apply` | применить политику (`dryRun=1` — предпросмотр) |
| `GET /api/backup/schedules` | список расписаний с вычисленным «следующим запуском» |
| `POST /api/backup/schedules` | создать или обновить расписание |
| `DELETE /api/backup/schedules/<id>` | удалить расписание |
| `POST /api/backup/schedules/<id>/run` | запустить расписание сейчас |
| `POST /api/backup/verify` | проверить копию (или все) на пригодность |

Требуется роль `operator` или `admin` — это действие, а не наблюдение.
Все запуски и отмены попадают в журнал аудита.

### Очередь заданий

- **Один рабочий поток.** Параллельные экспорты конкурируют за диск и сеть,
  и от этого хуже всем.
- **Переживает перезапуск.** История в `<dataDir>\backups\jobs\index.json`.
  Незавершённые задания после рестарта помечаются как прерванные — экспорт ВМ
  нельзя продолжить с середины, и делать вид, что он идёт, нельзя.
- **Отмена.** Движок проверяет флаг между шагами; уже скопированные файлы
  остаются на диске (их удаление — отдельное решение, не побочный эффект отмены).
- **Проверка результата.** После экспорта проверяется, что в каталоге есть
  и конфигурация (`.vmcx`/`.vmgs`), и хотя бы один диск. Пустой каталог
  бэкапом не считается — задание падает с внятным текстом.

### Гигиена инфраструктуры

`GET /api/hygiene?snapshotDays=30&stoppedDays=90` — осмотр того, что копится
незаметно и съедает место. **Ничего не удаляет**: только показывает.

| Что ищем | Как определяется | Зачем |
|---|---|---|
| Диски-сироты | файлы `.vhd`/`.vhdx`/`.avhdx`, не привязанные ни к одной ВМ | остаются после удаления машины, занимают десятки ГБ |
| Старые снимки | `CreationTime` снимка старше порога | чем дольше живёт снимок, тем дороже откат |
| Давно выключенные | время изменения файла конфигурации | машина, выключенная полгода, возможно не нужна |
| Крупные ВМ | суммарный размер дисков > 100 ГБ | для сведения |

### Ловушки, которые пришлось обойти

1. **Маска `*.vhd*` ловит служебные файлы.** Файлы отслеживания изменений
   (`<диск>.vhdx.rct`, `.mrt`) — не образы, удалять их нельзя. Расширение
   проверяется точно.
2. **Базовый диск снимка — не сирота.** После снимка активным становится
   `.avhdx`, а исходный `.vhdx` остаётся родителем. Родительские пути берутся
   из конфигураций снимков (`Msvm_VirtualSystemSettingData` со снимками):
   перечислять `Msvm_VirtualHardDiskSettingData` бесполезно — этот класс
   заполняется только явным вызовом метода.
3. **Конфигурация лежит не в корне.** Hyper-V хранит `.vmcx` в подкаталоге
   `Virtual Machines` внутри `ConfigurationDataRoot`, а не рядом с ним.

Из-за первых двух пунктов первая версия показывала 7 «сирот» вместо 1 — половина
из них была нужными файлами. Поэтому проверка делалась на живом хосте, а не
на бумаге.

## Логпак для поддержки

`GET /api/support/logpack` — архив со всем, что нужно для разбора, но **без
идентификаторов**. Собирается кнопкой «Собрать логпак» в настройках.

### Что внутри

| Раздел | Содержимое |
|---|---|
| `logs/` | журналы агента, последние 30 |
| `journal/` | журнал прогонов проверок, 3 месяца |
| `audit/` | журнал действий пользователей, 2 месяца |
| `state/` | текущее состояние заданий |
| `backups/` | задания, расписания, список копий (без содержимого) |
| `config/` | настройки, брендинг, компании |
| `diagnostics.json` | отчёт самодиагностики |
| `manifest.json` | что вошло, что пропущено, сколько замен |
| `README.txt` | пояснение для того, кто откроет архив |

### Чего нет и почему

- **`secrets.json`** — не включается вообще, даже обезличенный: сама структура
  ключей подсказывает, что искать.
- **`users.json`** — только сводка по ролям, без имён и хешей паролей.
- **Файлы бэкапов** — только имена и размеры.

### Как обезличивается

Замена **сквозная**: одно и то же значение всегда становится одним и тем же
плейсхолдером. Поэтому по архиву можно рассуждать («HOST-1 не отвечает час»),
но нельзя установить, что это за хост.

| Что | Становится |
|---|---|
| Пароли, токены, ключи, `dpapi:` | `<SECRET>` |
| URL с учётными данными | `https://<CREDENTIALS>@<HOST>/` |
| IP-адреса | `<IP>` / `<IP6>` |
| Почта | `<EMAIL>` |
| Домены и имена машин | `<HOST>` |
| Компании, ВМ, люди | `<COMPANY-N>`, `<PERSON-N>`, `<AGENT-N>` |
| Пути с именами | `C:\Users\<USER>\...` |
| Сетевые папки | `\\<HOST>\<SHARE>` |
| Имена файлов в архиве | `config/companies/_COMPANYID-1_.json` |

### Порядок замены — не случайный

Каждый шаг ловит то, что может испортить следующий:

1. **Секреты первыми.** Если пароль похож на IP, он должен стать `<SECRET>`,
   а не `<IP>`: утечка важнее читаемости.
2. **Почта до хостов.** Иначе `admin@server.local` распадётся на `admin@<HOST>`.
3. **Хосты до известных значений.** Если сначала заменить компанию, от
   `fileserver.secretcorp.local` останется `fileserver.<COMPANYID-1>.local`,
   и шаблон домена уже не сработает.
4. **IPv6 до IPv4.** Полная форма IPv6 содержит точки только в `::ffff:x.x.x.x`.

### Ошибки, найденные проверкой

Проверка делалась на живых данных: компания с настоящими IP, доменом, UNC-путём,
паролем в URL, ФИО и телефоном. Первые версии текли:

- **имя файла компании** выдавало `id` — теперь имена файлов обезличиваются;
- **UNC в JSON-экранировании** (`\\\\FS01\\backups`) не ловился выражением
  «две обратные косые» — теперь шаблон учитывает серии косых и сохраняет их
  число, чтобы JSON остался валидным;
- **пароль с `@` внутри** обрезался по первому `@`, оставляя хвост — теперь
  выражение жадно идёт до последнего `@` перед путём;
- **`fileserver.secretcorp.local`** терял только компанию, оставляя `fileserver.`
  — исправлено порядком замены.

## Выгрузка в CSV
`GET /api/export/csv?what=<набор>` — выгрузка любой таблицы интерфейса.

| Набор | Что выгружает |
|---|---|
| `backups` | задания бэкапа: объект, движок, состояние, размер, кто запустил |
| `copies` | копии на диске: имя, объект, время, размер |
| `audit` | журнал действий (только администратор), с учётом фильтров |
| `inventory` | ВМ: состояние, поколение, vCPU, память, диски, снимки, IP |
| `companies` | компании: источники, политика, удалённый агент, теги |
| `history` | состояния заданий проверок |

Особенности, из-за которых это не «просто CSV»:

- **Разделитель — точка с запятой.** Excel с русской локалью ждёт именно её;
  с запятой весь файл встаёт в одну колонку.
- **BOM обязателен.** `Encoding.GetBytes` его **не пишет** — preamble нужно
  добавлять отдельно, иначе Excel покажет «кракозябры». Проверено опытом:
  первая версия выгружала файл без BOM и открывалась мусором.
- **Даты в формате `yyyy-MM-dd HH:mm:ss`** — без `T` и `Z`, которые Excel
  не распознаёт как дату.
- **Права учитываются**: `audit` только для администратора, `companies` и
  `history` — только по видимым компаниям.

## Ссылки на задания

Каждое задание бэкапа адресуемо: `#/backups/<id>` открывает карточку с полными
деталями (движок, состояние, размер, длительность, кто запустил, каталог) и
готовой ссылкой для пересылки. При закрытии адрес возвращается к списку,
чтобы ссылка не «залипала» в истории браузера.

## Аудит действий
`GET /api/audit/list?limit=200&action=backup.&user=admin` — журнал того, кто что
делал. Только администратор: там видно, кто удалял компании и запускал бэкапы.

Журнал лежит в `<dataDir>\audit\yyyy-MM.ndjson`, показываются последние три
месяца. Фильтры — подстрока действия (`backup.`, `config.`, `login`) и имя
пользователя.

## Инвентарь виртуальных машин

Отдельная подсистема, не связанная с проверками: коллектор отвечает «всё ли
хорошо» и смотрит только отклонения, инвентарь отвечает «что у меня есть».

`GET /api/inventory?refresh=1` возвращает:

| Раздел | Что внутри |
|---|---|
| `host` | имя, ОС, ядра, память, диски со свободным местом |
| `vms[]` | имя, состояние, поколение, vCPU, память (стартовая/максимум/динамическая), диски с размерами, сетевые адаптеры с MAC, снимки, IP гостевой ОС, аптайм, heartbeat |
| `totals` | счётчики и **переподписка** |

### Переподписка

Считается как отношение выделенного к физическому:

```
cpuRatio    = сумма vCPU всех ВМ / ядер на хосте
memoryRatio = сумма памяти всех ВМ / памяти хоста
```

Предупреждение выводится при `cpuRatio > 4` или `memoryRatio > 1`. Это не ошибка
сама по себе — ВМ редко грузят все ядра одновременно, — но при массовом старте
машины начнут конкурировать за процессор. На тестовом хосте: **170 vCPU на 32
ядра = 5.31×**, и это честно показано в интерфейсе.

### Кэш

WMI по десятку ВМ отвечает секундами, поэтому результат кэшируется на 20 секунд.
Кнопка «Обновить» запрашивает мимо кэша (`refresh=1`).

### Управление ВМ: питание и снимки

Инвентарь — это чтение, управление — отдельный модуль `VmControl`
(`src/BackupDotNet.Core/Inventory/VmControl.cs`). Всё через WMI
`root\virtualization\v2`, без модуля Hyper-V и внешних библиотек.

| Действие | Метод WMI | API |
|---|---|---|
| Старт / выключение / пауза / перезагрузка | `RequestStateChange` | `POST /api/vm/power` |
| Список снимков | `Msvm_VirtualSystemSettingData` | `GET /api/vm/snapshots?name=ВМ` |
| Создать снимок | `CreateSnapshot` + `ModifySystemSettings` | `POST /api/vm/snapshot/create` |
| Откат к снимку | `ApplySnapshot` | `POST /api/vm/snapshot/apply` |
| Удалить снимок | `DestroySnapshot` | `POST /api/vm/snapshot/delete` |

Что выяснилось на живой ВМ — всё это записано в коде, чтобы не наступать дважды:

- **`TimeoutPeriod` не задаётся** из .NET Management API ни строкой, ни `DateTime`
  — метод отвечает «несоответствие типа». Работает и без него, ожидание
  асинхронного задания делаем сами.
- **Пауза — код 9 (Quiesce), возобновление — обычный Enable (2).** «Документные»
  32768/32769 дают «недопустимое состояние».
- **Имя снимка из `SnapshotSettings.ElementName` игнорируется.** Hyper-V всегда
  называет снимок «ВМ - (дата время)», поэтому имя задаётся вторым вызовом —
  `ModifySystemSettings` на настройках снимка.
- **`GetRelated` возвращает один снимок дважды**, поэтому список дедуплицируется
  по `InstanceID`.
- **Переходы асинхронные**: после ответа «запущено» агент ждёт фактического
  состояния (до 60 с), иначе интерфейс показывает «выполнено» при ещё
  выключенной машине.
- **Штатное выключение ВМ без гостевой ОС** падает с `0x800710DF`. Код
  переводится в человеческое «гостевая ОС не отвечает — используйте
  принудительное выключение».

Опасные действия (выключение, перезагрузка, сброс, откат снимка) помечены
в интерфейсе подтверждением: один клик не должен гасить продакшн-ВМ. Права —
как у остальных операций записи (`Roles.CanWrite`). Всё пишется в аудит
(`vm.power`, `vm.snapshot.create|apply|delete`).

### Создание ВМ

Мастер в инвентаре: `POST /api/vm/create`. Модуль — `VmCreator`
(`src/BackupDotNet.Core/Inventory/VmCreator.cs`), тоже чистый WMI.

Порядок шагов задан Hyper-V, а не удобством:

| Шаг | Как | Почему именно так |
|---|---|---|
| 1. Диск | `CreateVirtualHardDisk`, тип 3, VHDX | тип 2 — **фиксированный**: «10 ГБ» сразу занимают 10 ГБ на хосте |
| 2. Машина | `DefineSystem` без ресурсов | ресурсы, переданные сразу, Hyper-V отвергает |
| 3. vCPU и память | `ModifyResourceSettings` | оба ресурса у новой ВМ уже есть, «добавить» их нельзя |
| 4. Сеть | `AddResourceSettings` × 2 | порт и привязка к коммутатору — разные записи |
| 5. Диск в ВМ | SCSI-контроллер → дисковод → образ | у Gen2 диски живут только на SCSI |
| 6. ISO | дисковод DVD → образ | то же, через `Microsoft:Hyper-V:Virtual CD/DVD Disk` |

Три ошибки, которые стоили времени, — записаны в коде, чтобы не повторять:

- **`AddResourceSettings` требует `string[]`.** Одиночная строка превращается
  в скаляр, и Hyper-V отвечает «неверный параметр» (32773).
- **Переключатель не привязывается к порту.** Адаптер создаётся, но остаётся
  без сети: связь с коммутатором — отдельная запись
  `Msvm_EthernetPortAllocationSettingData` с `Parent` = путь порта и
  `HostResource` = путь коммутатора.
- **У адаптера нужен полный набор свойств.** Без `AllocationUnits`, `Weight`
  и `StaticMacAddress` — «не удалось изменить свойство Synthetic Ethernet Port».

MAC-адрес выдаётся при первом запуске, а не при создании — это нормально.

**Динамическая память** на некоторых хостах недоступна из-за раскладки NUMA
(«хост не может выделить память с такими параметрами»). Тогда агент откатывается
на фиксированную и пишет об этом в предупреждениях — машина создаётся в любом
случае.

**Шаблоны** (`<dataDir>\vm-templates\*.json`) — заготовки мастера: поколение,
vCPU, память, размер диска, коммутатор, автозапуск. Имя и размер диска при
создании всё равно задаются заново, иначе двадцать машин получили бы одно имя.

### Защита от разрушительных действий

Управление ВМ — это кнопки, которые гасят прод. Поэтому есть три уровня защиты
(`VmGuard`, `VmQuarantine`).

**1. Защищённые машины.** Шаблоны имён в `vm.protectedPatterns` (`*`, `?`,
регистр не важен): например `LH_*`, `DPT_*`. Машина с подходящим именем
помечается в таблице замком, и выключить, перезагрузить, откатить снимок или
убрать её в карантин можно только после подтверждения — ввода имени машины.
Не «запрещено навсегда», а «сначала осознай».

**2. Лимит массовых операций.** `vm.maxBatchSize` (по умолчанию 5) — больше
машин за один раз не обработать. Защищённые машины в пачке блокируют всю пачку.

**3. Карантин вместо удаления.** `vm.quarantineDays` (7 дней). Машина
выключается и переименовывается в `QUARANTINE_<имя>_<дата>`; диски остаются на
месте. Вернуть — одной кнопкой. Окончательное удаление вместе с дисками —
отдельный шаг, вручную, с подтверждением имени.

Права: выключение и снимки — `admin` и `operator`; карантин, окончательное
удаление и настройки — только `admin`.

**Dry-run** есть в двух местах: `POST /api/vm/create` с `dryRun: true`
возвращает список шагов и найденные проблемы, ничего не создавая;
`POST /api/vm/batch` с `dryRun: true` показывает, что было бы сделано и какие
машины пропущены защитой.

Два дефекта, найденные при проверке (оба — про то, что защита стояла не там):

- **Карантин не вызывал проверку.** API проверял права, но сама
  `VmQuarantine.Move` защиту не спрашивала — и `LH_DEB` уехала в карантин.
  Теперь проверка внутри `Move`/`Purge`, а не в обработчике.
- **`force` значил две разные вещи.** «Жёсткое выключение» и «обойти защиту»
  были одним флагом, поэтому кнопка жёсткого выключения проходила мимо защиты.
  Теперь это разные поля: `force` — про питание, `confirmProtected` — про защиту.

### Свободное место и прогноз

«Осталось 12 ГБ» само по себе ничего не значит — важно, за сколько дней они
кончатся. `SpaceTrend` хранит одну точку в день на диск в
`<dataDir>\space-history.json` (120 дней, ~9 дисков × 120 точек — файл
меньше 100 КБ).

Прогноз — прямая по методу наименьших квадратов через точки за последние
30 дней, а не разница «вчера-сегодня»: на VHDX-дисках место уходит ступеньками
(после бэкапа, после снимка), и по двум точкам линия врёт.

Порог тревоги — 30 дней до заполнения: это срок, за который ещё можно что-то
сделать. Меньше трёх точек — честное «копим: 1/3» вместо выдуманного прогноза.

Проверено на синтетике: −0.5 ГБ/день при 48 ГБ свободно → 97 дней,
−0.3 ГБ/день → 171 день, стабильно при 5 ГБ из 7 ТБ → тревога «свободно
меньше 10%, но место не убывает».

### ВМ без свежих копий

`VmStale` сверяет список ВМ с успешными заданиями бэкапа (`Status == "done"`,
неудачная попытка копией не считается). Машина попадает в отчёт, если
успешного бэкапа не было за `staleDays` (по умолчанию 30) или не было ни разу.

Это не ошибка: бэкапы мог делать кто-то другой. Но если про машину не помнит
ни журнал, ни расписание — в момент аварии окажется, что восстанавливать
нечего. Поэтому показываем, а не чиним.

### Отстойник сирот

Найденную сироту можно убрать — но не удалить. `OrphanTrash` переносит файл
в `<dataDir>\orphan-trash`, откуда он возвращается одной кнопкой; окончательное
удаление — отдельным шагом через `vm.quarantineDays` дней.

Три проверки до переноса:

| Проверка | Зачем |
|---|---|
| расширение `.vhdx` / `.vhd` | остальное к сиротам не относится |
| файл не привязан ни к одной ВМ | «не привязан» бывает обманчивым: конфигурация может лежать на отключённом диске |
| имя не подходит под `vm.protectedPatterns` | тот же механизм, что и для ВМ |

Если проверить привязку не удалось (ошибка WMI) — файл не трогаем:
неизвестность не повод удалять.

### Сеть: коммутаторы, адаптеры, VLAN

`GET /api/network` возвращает три среза: виртуальные коммутаторы (тип
External/Internal/Private, привязанный физический адаптер, число ВМ), адаптеры
ВМ с VLAN и сеть самого хоста (переиспользуется `NetConfigCollector`).

**Создание коммутаторов и привязка к физическому адаптеру не автоматизированы
сознательно.** Ошибка в привязке рвёт сеть хоста — а через неё доступ к самому
агенту. Такое делается из консоли Hyper-V, глядя на экран, а не кнопкой
из браузера.

Менять можно VLAN на порту ВМ: `POST /api/network/vlan`.

#### Почему VLAN идёт через PowerShell, а не WMI

WMI `ModifyFeatureSettings` на любой XML отвечает «ошибка не относится
к параметрам настройки виртуального коммутатора Ethernet» — проверено
с путём порта, с путём ВМ, с путём конфигурации, с `__PATH` и без него.
`AddFeatureSettings` срабатывает только когда записи VLAN ещё нет.

Командлет `Set-VMNetworkAdapterVlan` делает то же самое с первого раза.
Поэтому `NetworkInventory.ApplyVlan` вызывает его через `PsBridge` —
`System.Management.Automation` из GAC (разрешено правилами, сторонних
пакетов нет).

Что выяснилось про VLAN в Hyper-V:

| Что | Как на самом деле |
|---|---|
| Режим Access | `OperationMode = 1` (не 0) |
| Режим Trunk | `OperationMode = 2` |
| «Без тега» | записи VLAN нет вообще, а не `AccessVlanId = 0` |
| `InstanceID` записи | `<порт>\C\952C5004-4465-451C-8CB8-FA9AB382B773\<guid>` |
| `AffectedConfiguration` для Add | путь **порта**, не конфигурации ВМ |
| Обязательные поля при Add | `Caption` и `Description`, иначе «неверный параметр» |

#### Защита от обрыва связи

Смена VLAN рвёт связь с машиной — это её смысл. Поэтому:

1. **Машина, в которой работает агент,** — отказ без вариантов. Если имя хоста
   совпадает с именем ВМ, VLAN менять нельзя: после смены мы потеряем и её,
   и себя.
2. **Работающая ВМ с одним адаптером** — требует подтверждения вводом имени.
   Выключенная или многoадаптерная — меняется сразу, риска нет.
3. Защищённые ВМ (`vm.protectedPatterns`) — как и везде, через `VmGuard`.

### Хранилища

`GET /api/storage` — доступность целей из `storage.targets` плюс
`backup.destination`. `POST /api/storage/check` проверяет произвольный путь,
не добавляя его в настройки.

Зачем отдельно от дисков хоста: бэкап пишется не «на C:», а на конкретную
сетевую папку. Папка может быть недоступна по десятку причин — упал сервер,
закрыли шару, кончились права, — и агент молчит, пока бэкап не упадёт ночью.

Что проверяется:

| Что | Как | Зачем |
|---|---|---|
| Доступность | `Directory.Exists` в отдельной задаче с таймаутом 15 с | мёртвый UNC висит десятками секунд и вешает запрос |
| Место | `GetDiskFreeSpaceEx` через Win32 | `DriveInfo` не работает для UNC |
| Запись | создать файл, прочитать обратно, удалить | «папка видна» и «в неё можно писать» — разные вещи |
| iSCSI | `MSiSCSIInitiator_SessionClass` | пустой список — норма, а не ошибка |

Пробный файл — 40 байт с именем `.bnd-write-test-<8 hex>.tmp`; удаляется
в `finally` даже при ошибке. Если удалить не удалось — это не повод падать.

Проверено на реальном: локальный каталог и шара `\\DPTSRV0\pub_e` — доступны
и пишутся; `\\NONEXISTENT-SRV\share` — «путь не найден» за 2.3 с;
`\\10.255.255.1\share` — ровно 15 с и «сервер не отвечает». Мусора после
проверки записи не остаётся.

## Проверка копии
Кнопка «Проверить» рядом с копией (или `POST /api/backup/verify`) прогоняет
структурную проверку:

| Что | Как | Зачем |
|---|---|---|
| Конфигурация | есть `.vmcx`/`.xml` | без неё ВМ не импортируется |
| Диски | есть `.vhdx`/`.vhd` | копия без диска бессмысленна |
| Подпись VHDX | `vhdxfile` в начале, `head` по 64 КБ | ловит чужой файл вместо образа |
| Выравнивание VHDX | размер кратен 1 МБ | ловит обрыв записи |
| Подпись VHD | `conectix` в последних 512 байтах | ловит обрезанный VHD |
| Размер | сверка с записанным при создании | ловит недокопированную копию |

Почему не монтируем и не поднимаем ВМ: монтирование требует полных прав
администратора, а пробный импорт ВМ через WMI привязывает диски к **исходным**
путям (две ВМ на одном VHDX — риск порчи). Поэтому проверка честно называется
структурной и говорит об этом в окне результата.

### Расписания

Планировщик — отдельный поток рядом с очередью: сам ничего не копирует, только
решает «пора» и ставит задания. Очередь умеет отмену и прогресс, расписание
не должно в это вмешиваться.

Формат сознательно не cron: администратору нужно «каждую ночь в 2:00», а не
«0 2 * * *». Правится без шпаргалки.

```json
{
  "id": "nightly-vm",
  "title": "Ночной бэкап ВМ",
  "enabled": true,
  "engine": "hyperv-export",
  "targets": ["BND_TEST_01", "DPT_DEB_11"],
  "daysOfWeek": [1, 3, 5],
  "timeOfDay": "02:00",
  "windowFrom": "22:00",
  "windowTo": "06:00",
  "retries": 2,
  "retryDelayMinutes": 30
}
```

Хранятся в `<dataDir>\backups\schedules.json`, правятся из интерфейса.

**Четыре предохранителя**, без которых планировщик бэкапов опасен:

1. **Окно запуска** — не начинать копирование в рабочее время. Окно может
   пересекать полночь (`22:00–06:00`).
2. **Пропуск навёрстывания** — если агент был выключен сутки, все пропущенные
   запуски не идут пачкой. Опоздание больше 3 часов → запуск пропускается
   с записью в журнал, ждём следующего по расписанию.
3. **Повтор с задержкой** — упавшая ВМ не молотит каждую минуту, а ждёт
   `retryDelayMinutes`.
4. **Своё задание на каждый объект** — одна недоступная ВМ не блокирует
   копирование остальных.

**Опорная точка — сохранённый `NextRunAt`,** а не пересчёт «от сейчас» на каждом
тике. Пересчёт давал окно срабатывания шириной в пару минут: тик, попавший чуть
позже, молча пропускал запуск.

### Политика хранения копий
Бэкапы занимают место быстро, поэтому удаление — часть работы, а не уборка «когда-нибудь».

```json
{
  "backup": {
    "destination": "H:\\Backups",
    "retention": {
      "keepCount": 7,
      "keepDays": 14,
      "gfs": { "daily": 7, "weekly": 8, "monthly": 12 },
      "protectLast": true,
      "maxDeletePerRun": 10
    }
  }
}
```

| Ключ | Смысл |
|---|---|
| `keepCount` | всегда хранить N последних копий |
| `keepDays` | всё, что моложе N дней, не трогать |
| `gfs.daily` | по одной копии за каждый из N последних дней |
| `gfs.weekly` | по одной за каждую из N недель (ISO 8601) |
| `gfs.monthly` | по одной за каждый из N месяцев |
| `protectLast` | никогда не удалять самую свежую копию |
| `maxDeletePerRun` | предохранитель: не больше N удалений за проход |

Почему GFS, а не «хранить 7 последних»: простое окно плохо переживает отпуск.
Через месяц остаются только свежие копии, и откатиться на состояние
«до обновления в прошлом квартале» некуда. GFS держит цепочку: дни подробно,
недели и месяцы — редко, но долго.

**Три предохранителя**, потому что уборка необратима:

1. Последняя копия защищена всегда — даже если политика говорит обратное.
2. Лимит удалений за проход: ошибка в настройках не снесёт весь архив сразу.
3. Предпросмотр (`dryRun`) показывает, что будет удалено, с причиной по каждой копии.

Уборка запускается автоматически после успешного бэкапа и вручную кнопкой
«Применить». Ошибка уборки не портит статус успешного бэкапа.

### Ограничения, о которых сказано прямо
| Ограничение | Почему |
|---|---|
| Нет VSS-снимка тома | экспорт работающей ВМ даёт копию «как есть»; для транзакционной консистентности приложения нужен снимок (этап 3.4) |
| Нет сжатия | размер результата близок к сумме дисков; архивация — этап 3.4 |
| Нет инкремента | каждая копия полная; дельта — этап 3.4 |
| Нет выбора дисков | копируются все диски ВМ; фильтр — этап 3.1 (остаток) |

### Права

Нужны права администратора Hyper-V: членство в группе **Hyper-V Administrators**
достаточно, полное повышение прав не требуется. Если прав нет — движок честно
сообщает об этом на странице «Бэкапы», а не падает с невнятной ошибкой WMI.

## Хранение истории и обновления

### Политика хранения

История растёт непрерывно, поэтому окно хранения задаётся явно
(`config/settings.json` → `history`):

| Ключ | По умолчанию | Что ограничивает |
|---|---|---|
| `journalKeepDays` | `400` | подробный журнал прогонов (`journal/yyyy-MM.ndjson`) |
| `rollupKeepMonths` | `60` | суточные сводки (`rollups/`) |
| `autoPrune` | `true` | удалять ли старое при запуске агента |

Журнал хранится файлами по месяцам, поэтому удаляются только месяцы, целиком
попавшие за порог: текущий месяц не обрезается никогда. Прибрать вручную —
кнопка «Прибрать» в настройках или `POST /api/history/prune`.

### Проверка обновлений

Два источника на выбор (`updates.source`): локальный каталог для контуров без
интернета и GitHub Releases для машин с доступом наружу.

#### Локальный каталог (по умолчанию)

```json
{
  "updates": {
    "enabled": true,
    "source": "local",
    "path": "\\\\fileserver\\BackupDotNet\\latest"
  }
}
```

В каталоге лежит `latest.json`:

```json
{
  "version": "1.2.0",
  "date": "2026-11-20",
  "file": "BackupDotNet-1.2.0.zip",
  "notes": "Что нового — одной строкой."
}
```

Агент сравнивает версии и показывает «Доступна версия 1.2.0». Скачивать
и устанавливать он не пытается — это осознанно оставлено человеку.

#### GitHub Releases

```json
{
  "updates": {
    "enabled": true,
    "source": "github",
    "githubRepo": "dpteam/BackupDotNet",
    "allowInstall": true
  }
}
```

Проверка идёт через `GET /repos/{repo}/releases/latest`. Берётся первый `.zip`
из приложений релиза. Для приватного репозитория нужен токен: положите его
в `secrets.json` под ключом `updates.githubTokenSecret`.

Для GitHub Enterprise задайте `updates.githubApiBase`, например
`https://github.company.local/api/v3`.

#### Установка

`allowInstall: true` разрешает ставить обновление кнопкой. По умолчанию
**запрещено**: скачать архив можно, но подменять файлы — только осознанно.

Порядок установки:

1. архив скачивается в `<dataDir>\updates\download`;
2. проверяется контрольная сумма от GitHub (если есть) и структура архива;
3. распаковывается в `<dataDir>\updates\staging\<версия>`;
4. по команде установки создаётся скрипт `<dataDir>\updates\apply-update.cmd`,
   который ждёт выхода агента, копирует текущую версию в
   `<dataDir>\updates\backup\<версия>-<время>`, заменяет файлы (не трогая
   `config`, `data`, `auth`) и запускает агент обратно;
5. агент завершается — скрипт делает свою работу.

Почему так, а не «скопировать поверх»: подмена файлов работающего процесса на
Windows почти всегда даёт полуобновлённый каталог — exe занят, часть dll
скопирована, служба не стартует. Отложенная установка стоит одного перезапуска
и даёт дешёвый откат.

**Откат:** остановить службу, скопировать содержимое
`updates\backup\<версия>-<время>` обратно в каталог программы, запустить.
Скрипт пишет отчёт в `updates\install.log`.

#### Проверка без GitHub

Анонимный лимит GitHub — 60 запросов в час на IP, при отладке он исчерпывается
быстро. В комплекте есть заглушка:

```powershell
powershell -ExecutionPolicy Bypass -File tools\mock-github-api.ps1 `
  artifacts\BackupDotNet-1.0.1.zip 1.0.1

# в настройках: "githubApiBase": "http://127.0.0.1:9099"
```

Третий аргумент `bad` заставляет заглушку отдавать неверную контрольную сумму —
удобно проверять, что агент откажется ставить испорченный архив.

## Самодиагностика

`Diagnostics.Build()` в ядре собирает отчёт «а всё ли в порядке» — без действий и
без исключений. Отчёт отдаётся по `GET /api/diagnostics` и рисуется на странице
**Здоровье** (обновляется каждые 15 секунд).

Проверки (каждая — `ok` / `warn` / `error`):

| Проверка | Что смотрит |
|---|---|
| Диск с данными | свободное место: `< 2 ГБ` — предупреждение, `< 0.5 ГБ` — ошибка |
| Конфигурация | ошибки чтения `settings.json`, компаний, секретов |
| Планировщик | поток жив, длительность тика, сколько прошло с последнего тика |
| Веб-сервер | занятый префикс; `localhost` — предупреждение, что сеть не видна |
| Авторизация | включена ли `web.requireAuth` |
| Zabbix | включён ли sender, размер очереди на досылку |
| Журналы | каталог задан, файл реально пишется |
| Хранилище | состояние читается, сколько заданий |

Дополнительно отдаются сведения о процессе (память, потоки, хэндлы), среде
(.NET, ОС, разрядность), путях, размерах каталогов и правах учётной записи.
Всё это нужно, чтобы разбирать инцидент по одному экрану, а не по десяти командам.

## Безопасность

- Пароли пользователей — PBKDF2 (`Rfc2898DeriveBytes`), соль на пользователя.
- Сессии — случайный токен в cookie `bc_sess`, срок из `web.sessionTimeoutMinutes`.
- Секреты источников — в `config/secrets.json`, шифруются DPAPI `LocalMachine`
  (префикс `dpapi:`), в открытом виде не пишутся.
- Статика отдаётся только из `publicDir`; выход за каталог отсекается
  сравнением `Path.GetFullPath`.
- API журналов принимает только `Path.GetFileName` — обойти каталог нельзя.
- Роли: `admin` (всё), `operator` (правка компаний, запуск), `viewer` (чтение),
  `client` (только свои компании).

## Параллелизм

- Планировщик — один фоновый поток (`Thread`), проверки — `Parallel.ForEach`
  с `MaxDegreeOfParallelism`.
- `DataStore` защищён внутренним локом; запись — под ним же.
- `WebHost` принимает соединения в цикле, обработка — в `ThreadPool`.
- `Log` синхронизирован одним локом; файловый листенер — своим.

## Расширение

Новый источник проверки:

1. Создать класс в `Core`, реализующий `ICollector`.
2. Зарегистрировать в `Collectors` (статический конструктор).
3. Добавить `case` в `ApiHandler.NormalizeSourceType` (если нужна валидация).
4. Добавить описание в `SOURCE_TYPES` в `public/js/app.js` (для формы).
5. Описать параметры в `docs/SOURCES.md`.

Никаких изменений в планировщике, хранилище и политиках не требуется.
